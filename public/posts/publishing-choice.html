技術文章要發在哪：平台專欄還是自己架站

決定要寫一系列技術文章之後，我以為下一步是開寫。結果第一步就卡住了——發到哪裡。

這件事看起來瑣碎，其實決定了你之後所有的自由度：你的讀者在哪、你的內容歸誰、你想改版時能不能改、十年後這些文章還在不在。所以比起急著產出，我先把「平台專欄」和「自己架站」這兩條路攤開來比，權衡清楚了再動筆。下面這篇，就是我的比較與結論。

先定義：兩條路長什麼樣

方案一：去現有平台開專欄。 你不用管主機、不用管樣式，註冊一個帳號就能寫。國內常見的有掘金、CSDN、知乎專欄、部落格園；國際上有 dev.to、Hashnode、Medium、Substack。好處是平台自帶讀者池與推薦機制，文章發出去就有機會被看見。

方案二：自己架網站。 這裡又分兩種姿態：

  • 靜態生成（我這個部落格就是）：用 Markdown 寫，一個腳本編譯成純 HTML，丟到 Netlify / GitHub Pages / Vercel 這類靜態主機就好。沒有後端、沒有資料庫、沒有審核。
  • 自建 CMS（如 WordPress）：要租主機、裝程式、管資料庫，功能最完整，但也最重。

下面我把這兩條路（平台、自架靜態、自架 CMS）放在五個你點名的維度上一起比。

建置成本

平台完勝，這點不用辯。自架靜態站的一次性成本其實很小——像我這個站，核心就是一個 Node 腳本加一份 CSS，半天就能跑起來，之後託管幾乎免費。真正貴的是 CMS 那條路：主機、域名、維護時間，長期加起來不是小數目。

維護難度

平台同樣是零。但自架靜態站其實也接近零——因為它只是一堆檔案，沒有會過期的服務要盯。真正的維護噩夢是 CMS：今天外掛衝突、明天要升版本、後天出安全漏洞。我自己的判斷是，如果沒有強烈需要動態功能，CMS 的維護成本不值得。

內容掌控度

這是天平傾斜最明顯的一格。平台專欄的本質是「借地方寫」：排版被限制、資料難匯出、政策一變你就得跟著變，極端情況是帳號被封或平台收攤，心血跟著不見。自架站的核心價值，就是「東西是你的」——Markdown 源檔在你硬碟裡，想搬去任何主機都行，沒人能審你的內容，也沒演算法決定誰看得到。

SEO

平台的優勢是「起步權重」：新文章容易借到網域的權威而被搜到。但長期看，自架靜態站會把權威累積在自己網域上——你寫得越久，舊文章越容易被搜尋到，這是平台給不了的複利。缺點是要自己補 sitemap、Open Graph、canonical 這些（後面步驟會提到）。CMS 最強，但對多數技術部落格來說，靜態站補好基本 SEO 已經綽綽有餘。

長期經營彈性

平台把你鎖在它的框架裡：想加個互動範例？想接自己的分析工具？想做會員制？多半做不到或很彆扭。自架站相反——靜態站想加搜尋、留言、甚至電子報，寫點前端就能接；CMS 更是不設限。技術文章尤其吃這點：你常需要嵌入可執行範例、版本演進的比較、跨文章連結，自架站能做到最順。

技術文章的特殊性：為什麼我更偏自架

上面是通用比較。但「技術文章」這個主題性質，會把天平再往自架推一點：

  • 代碼與排版：技術文滿是程式碼區塊、終端輸出、架構圖。自架站可以完美控制 syntax highlight、行號、深色模式；平台的編輯器常常把程式碼排得歪七扭八，或根本不支援你想要的語言。
  • 可執行與可驗證：你希望讀者能複製、能跑。自架站能嵌 CodePen、能連到自己的 repo；平台則視其政策而定。
  • 版本與演進：技術會過時。自架站你隨時能回去修一篇三年前的文章、加「2026 更新」註記；平台雖也能編輯，但版本歷史與匯出通常不友善。
  • 跨連結與系列感：一系列文章彼此引用，自架站內部連結零成本，還能做成專題頁；平台專欄的「系列」多半只是標籤聚合，體驗差一截。

我的情況：技術能力與已有基礎

決策不能脫離自身條件。攤開我自己的牌：

  1. 我已經有一個自架靜態部落格（就是現在這個）——Markdown 寫、Node 腳本編譯、零主機費。等於方案二的基礎設施已經 zero-cost 就位。
  2. 我習慣用 Markdown 與版本控制，也寫得動一點前端／腳本。維護靜態站對我不是負擔，反而是舒適圈。
  3. 主題是技術文章——如上面所說，這類內容在自架站能得到最好的呈現。

這三點加起來，平台專欄對我最大的誘因（「省事、有現成流量」）就打了折扣：省事這部分我已經自家解決了，剩下的「現成流量」則可以用別的方式補（見下）。

我的選擇：自架為主，平台分發為輔（混合策略）

結論很清晰——以自架靜態站為主陣地，再選 1–2 個平台做分發（syndicate）。

  • 主陣地自架：內容主權、SEO 複利、排版自由全拿。這裡是你真正的「家」，所有原稿、所有連結都歸你。
  • 平台分發：把文章（或節錄）同步到 dev.to（國際技術圈）/ 掘金（中文技術圈）等 1–2 個平台，目的是觸及。關鍵是每篇都放「原文連結」回自己的站，把平台讀者慢慢導回主陣地。這樣既借到平台的起點流量，又不把命脈交出去。

這個組合避開了兩端的極端：純平台（主權喪失）、純自架（冷啟動沒讀者）。技術寫作圈其實普遍這樣做——你會看到很多作者的文章同時出現在個人站和 dev.to 上。

什麼情況下我會改推「純平台」？如果你完全不想碰任何技術設定、且主題是泛大眾而非硬核技術（例如生活隨筆），那平台專欄的省事就值得。但既然是技術文章、且我已自架好，這條不適用。

什麼情況下我會改推「純自架 + 不要平台」？如果你寫的內容極敏感、怕被平台審下架（比如某些爭議醫療觀點），那就只留自架，靠 RSS 與口耳相傳散播，不依賴任何演算法。

後續步驟規劃

決定自架為主後，可以照這個順序動：

  1. 定主題與排程：先列出這一系列要寫的 5–8 篇、彼此順序、預計頻率。技術系列最忌「寫一篇斷半年」，有骨架才寫得下去。
  2. 補強 SEO（自架站的必要功課）：給編譯器加 sitemap.xml、每頁 Open Graph / Twitter Card 標籤、canonical 指向自己網域；申請並綁定一個自有域名（網域權威累積的前提）。這幾項我這個靜態站目前還沒做，是接下來要補的。
  3. 自動化部署：把 source/ 推到 GitHub，串 Netlify / Vercel 的「push 即部署」，以後寫完 git push 就上線，不用手動傳檔。
  4. 選平台做分發：挑 1–2 個（建議 dev.to + 掘金），建立發文 SOP：原文在自己站先發，隔天貼到平台並加上「原文連結」。
  5. 輕量、重隱私的數據：若要衡量成效，用 Plausible / GoatCounter 這類不追蹤個人的分析，而不是 Google Analytics。技術讀者普遍在意隱私，這也呼應這個部落格「不綁架讀者」的姿態。

小結：一張極簡決策表

  • 主題是硬核技術 + 你願意碰一點設定 → 自架靜態站為主 + 平台分發。✅（我的選擇）
  • 主題泛大眾 + 你完全不想碰技術 → 直接平台專欄。
  • 內容極敏感怕被下架 → 純自架，靠 RSS 散播。

寫技術文章，最珍貴的資產不是某篇爆文，而是一個你完全掌控、能長期累積的場子。平台來來去去，自己的網域與原稿不會。想清楚這點，第一步該往哪走，其實不難。
